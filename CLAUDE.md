# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

FGB Monitoring — a real-time energy / air-quality / water monitoring dashboard for smart buildings
(retail sites of luxury holdings). React 18 + TypeScript + Vite + shadcn-ui + Supabase, shipped as a
web app, a PWA, and native iOS/Android apps via Capacitor. Originally scaffolded with Lovable, which
is **still in active use on `main`**.

## Commands

```sh
npm run dev                              # dev server on :8080 (add -- --host to reach it from a phone)
npm run dev -- --mode demo --port 8081   # demo mode: .env.demo blanks the Supabase vars -> mock data, no login
npm run build                            # production build to dist/
npm run lint                             # eslint
npx tsc --noEmit -p tsconfig.app.json    # typecheck (there is no `typecheck` npm script)
```

There is **no test framework** in this repo. Verification = typecheck + lint + looking at the app in
the browser (both desktop and a 390px-wide mobile viewport).

**Known baseline before you start:** `tsc` reports 4 pre-existing errors and `eslint` reports ~357
problems (281 errors). Compare against that baseline rather than expecting zero — and don't
bulk-fix them as a side quest.

Native builds: `npx cap sync` after any dependency or `dist/` change, then `npx cap open android|ios`.
`capacitor.config.ts` has no `server.url` block — do not add one to a release build.

## Architecture

### Data hierarchy

Everything hangs off a four-level chain, and most bugs come from confusing its levels:

```
holding (Kering)  ->  brand (Gucci)  ->  site (a physical store, has lat/lng/timezone/area_m2)
                                            -> project == row in `site_config` (module gating, thresholds)
                                            -> devices -> telemetry
```

`Project` (`src/lib/data.ts`) is the frontend view model; `AdminProject`/`AdminSite`
(`src/lib/types/admin.ts`) are the admin/DB shapes. A `Project` carries a `siteId` (a real UUID) —
prefer matching on it over matching on names, and validate with `isValidUUID` from `src/lib/utils.ts`
before hitting the DB (several demo/mock sites have non-UUID ids and will otherwise throw Postgres errors).

### The single-page dashboard

`src/pages/Index.tsx` is the whole product: a Leaflet world map with clustered `SiteMarker`s, plus
stacked overlays (`RegionOverlay` -> `BrandOverlay` -> `ProjectDetail`) rather than routes. Routing is
`HashRouter` (`src/App.tsx`) because the app is served from GitHub Pages under a subpath — only
`/auth`, `/`, `/admin`, `/install` exist.

`ProjectDetail.tsx` (~7.2k lines) is the per-site dashboard: a horizontal carousel of sections
(`overview | energy | air | water | certifications`, the `ProjectSection` type in `SiteMarker.tsx`).
It is the known structural debt of the codebase — split work on it carefully, and if Lovable ever
rewrites it, re-check that the PDF-export `useCallback` stays **above** `if (!project) return null;`
(Rules of Hooks).

Mobile has dedicated components rather than pure CSS breakpoints: `OverviewMobileView`,
`MobileKpiPanel`, `MobileBurgerMenu`.

### Access control

`useUserScope()` derives a `ClientRole` (`ADMIN_FGB | USER_FGB | ADMIN_HOLDING | ADMIN_BRAND | STORE_USER`)
purely from the `user_memberships` table plus `user_roles`. **Never re-introduce email-based role
inference** — the fallback on any error or missing membership is deliberately the least-privileged
`USER_FGB`. The Supabase anon key is public by design, so **RLS policies are the only barrier on
customer data**.

### Module gating

Each project enables `energy` / `air` / `water` / `certification` independently.
`useProjectModuleConfig(project)` resolves the config (demo showcase sites are hardcoded in
`src/lib/data/demoSiteMocks.ts` and deliberately ignore the DB), and `ModuleGate` renders either the
real content, a locked notice, or an opt-in demo dashboard.

### Real data vs mock — the rule that matters most

`isSupabaseConfigured` in `src/lib/supabase.ts` (true only when both `VITE_SUPABASE_URL` and
`VITE_SUPABASE_ANON_KEY` are set) drives everything. When it's false the app runs on mocks and skips
login.

**Mock data must never be presented as real.** A telemetry failure has to degrade to empty series and
a `NO_DATA` state — not to plausible-looking fake numbers, and never to a "Live" badge. Every chart
carries a `DataSourceBadge` fed by the `isRealData` flag that the data hooks return alongside
`{ data, isLoading, isError, refetch }`.

`src/integrations/supabase/client.ts` is **auto-generated by Lovable — never hand-edit it.**
`src/lib/supabase.ts` imports that single instance (two clients caused duplicate GoTrueClient/session
conflicts); keep the dependency in that direction.

### Data layer

- `src/lib/api.ts` — typed fetchers + React Query hooks + `queryKeys`. Contains `normalizeMetric`/
  `toDbMetricCandidates`: metrics are canonically dotted (`iaq.co2`, `energy.active_power`,
  `env.temperature`) but historical rows use short aliases (`co2`, `temp`, `tvoc`), so queries fan out
  over candidate names. Add new aliases there, not at call sites.
- `src/hooks/` — feature hooks (`useRealTimeTelemetry`, `useAggregatedSiteData`, `useTimeFilteredData`,
  `useSiteThresholds`, …).
- `src/contexts/AdminDataContext.tsx` — loads holdings/brands/sites/projects/memberships at mount and
  exposes CRUD. It is a known bottleneck (~900 lines, eager load); migrating it to React Query is a
  planned, dedicated piece of work, not something to do incidentally.
- `src/contexts/LanguageContext.tsx` — i18n as one flat `key -> {en,it,fr,es,zh}` map. Five languages;
  hardcoded Italian strings scattered in components are a known defect to migrate here, and **all new
  in-app text must be English** (plus the other four keys).

### Backend (do not modify without an explicit ask)

- `supabase/migrations/` + `supabase/functions/` — Postgres schema and Deno edge functions
  (`timeseries`, `latest`, `devices`, `energy-diagnosis`, `analyze-bill`, `scheduled-jobs`, …).
  The `timeseries` function auto-selects raw / hourly / daily aggregates by range width.
- `mqtt-ingestion/` (repo root) — **the production ingestion service and the source of truth.** It
  handles live customer data; leave it alone.
- `services/mqtt-ingestion/` — an obsolete, divergent copy kept only pending the owner's go-ahead to
  delete. Never edit it, never use it as reference.

Aggregation is scheduled by **pg_cron inside the database** (hourly `run_scheduled_jobs()` at :05,
daily `run_daily_jobs()` at 01:30, batched purge at :45). `.github/workflows/scheduled-jobs.yml` is
`workflow_dispatch`-only: a manual catch-up lever, not a clock — its cron was removed in Sep 2026
because it fired at the same minute as pg_cron and the two collided.

### Deploy

Push to `main` triggers `.github/workflows/deploy.yml` -> GitHub Pages. `vite.config.ts` sets
`base: "./"` for builds (relative asset paths for subpath hosting) and keeps `/` in dev. The PWA
service worker is disabled in dev/preview on purpose — enabling it breaks the Lovable iframe preview.
`console.log`/`console.debug` are stripped from production builds only.

## Working rules (from the owner)

1. **Work directly on `main`.** No feature branches. This supersedes `HANDOFF.md`, which still says
   the opposite — that document is outdated on this point only.
2. One change = one small, revertible commit, with a message explaining the cause. Typecheck and look
   at it in the browser before committing.
3. This code serves real customers in production. No unrequested invasive refactors.
4. For meaningful UI changes, produce a navigable mockup (artifact) and iterate on it **before**
   writing code.
5. Product decisions (which modules to expose, opt-outs, what to keep) are the owner's call — surface
   them, don't decide them.
6. Brand palette: `#9fd5d9`, `#009193`, `#016368`, `#931841`, `#f9cace`. Red/pink signals problems only.
   Icons always from `lucide-react`, never a different visual vocabulary.
